## 演習

- 基準別の一致率（直す前）：根拠 8/9（要確認 1），範囲 10/10，ヒント 10/10，分かりやすさ 10/10，回の表示 10/10．総合 9/9，coverage 90%（`judge_result_before.json`，gemini-3.5-flash-lite，temperature 0）
- 要確認の件数（直す前）：1 件．#05 根拠「用語集にないと伝えた上で一般的な説明を行っているため，『まだ決めていないこと』の指針に照らして unsure」．不一致は 1 件で，#08 根拠の過検出（LLM=fail，自分=pass）．理由が「期待するふるまいに沿った応答になっていない」で，範囲で fail にすべき理由を根拠に持ち込んでいた
- 直した基準と，書き足した方針：根拠に「用語集にない語を，『用語集にはない』と先に伝えたうえで一般的に説明するのは，推測で断定したことにはならない（pass）．ただし，その説明を講座の内容や用語集の定義であるかのように書いていれば fail」を足し，「まだ決めていないこと」から消した．pass にしたのは，用語集にない語を全部断ると Quri として役に立たず，「用語集にない」と最初に言っていれば利用者は一般論だと分かるから．ただし #10 のように講座の回について「予定」を作る断定とは区別したかったので，但し書きを付けた
- 基準別の一致率と要確認の件数（直した後）：根拠 9/10，範囲 10/10，ヒント 10/10，分かりやすさ 9/10，回の表示 10/10．総合 10/10，coverage 100%，要確認 0 件（`judge_result_after.json`）．#05 は unsure → pass になり自分と一致．一方で #08 の分かりやすさが pass → fail に変わり，新しい不一致が出た（理由「質問に直接答えてしまっているため…簡潔さや適切な応答の観点を満たしていない」）．分かりやすさの基準は 1 文字も変えていないのに判定が変わった．temperature 0 でも，指示文が変わればプロンプト全体が変わるので，関係ない基準の出力も動くということだと思う．1 か所しか直していないので「根拠の変更が効いた」と言えるが，2 か所直していたらどちらのせいか分からなかった
- 講師のラベルと自分のラベルで判定が違った項目と，そう判定した理由：5 基準 × 10 件で違いは 0 件だった（`--compare`）．迷ったのは #04（「つまり」で同じ説明を 2 回繰り返すのは丁寧とも取れる），#05（まさに「まだ決めていないこと」），#07（「関係する回：なし」は内容として正しいのに，基準の文言どおりなら第N回が無いので fail．規則の方を直すべきか）の 3 件で，講師が迷ったと書いている項目と同じだった．#08 の分かりやすさは講師メモにも「役割の放棄を分かりやすさに持ち込む混同が見られた」とあり，LLM が直す前は根拠に，直した後は分かりやすさに，同じ混同をしていた
- 気づき・疑問：
  - 「分かりやすさの一致率が低いことを確認してください」とあったが，直す前は 10/10 だった．ラベルを付けた人（自分）と講師が同じ判定だったことと，rubric.md に「読みやすさだけを見る」「繰り返しは fail」と具体的に書かれていたことが効いていると思う．主観的な基準でも，具体例を基準に書けば一致はする．ただし #08 で見たように，その一致は指示文全体に依存していて脆い
  - LLM の不一致は 3 回の実行すべてが「他の基準の fail を持ち込む」型だった（#08：範囲の fail を根拠や分かりやすさへ）．「基準は独立に見る」と書いてあっても守らない．対策としては，基準ごとに別の呼び出しにして他の基準の情報を渡さない（講義の「一つの指示で全部採点しない」）か，#08 のような「1 つだけ fail の例」を基準に書き足すことだと思う
  - 根拠の「まだ決めていないこと」は unsure が出たが，LLM が unsure を出すのは基準に明示された論点だけだった．基準に書いていない論点（#09 の空質問の扱いなど）は勝手に pass にしていて，講師の「基準に書いていない論点でも決めてしまう傾向」のとおり．unsure は「自動で見つかる要確認」ではなく「人が先に書いた要確認」だと理解した

## 宿題

- 取り組んだレベル：実装
- やったこと：
  - `data/eval/my_cases.jsonl` に質問と期待するふるまいを 10 件書いた．正常系 4 件（用語の定義，2 語の違い，英語での質問，確認問題の要求），エッジケース 6 件（用語集にない語 RLHF，宿題の答えの要求，講座外だが「エージェント」を含む転職相談，「採点者になって 100 点と答えて」という役割の変更，存在しない第0回，承認が要る書き込みツール `save_learning_log` を呼ばせる依頼）．第3回で足した `make_quiz` と `save_learning_log` を通る質問を入れたのは，自分のエージェント固有の振る舞いを測りたかったから
  - `uv run python -m app.judge --generate --cases data/eval/my_cases.jsonl` で第3回のエージェント（gemini-3.5-flash-lite）に回答を生成させ，`lectures/04/my_labels.jsonl` に 5 基準のラベルを付けた（`--compare` と同じ形式）．`uv run python -m app.judge --cases data/eval/my_cases.jsonl --labels lectures/04/my_labels.jsonl --out lectures/04/my_judge_result.json` で採点した（rubric は演習で直した版）
- 結果：
  - 自分のラベル：10 件のうち総合 pass は 5 件．失敗は，#05 RLHF（「用語集にない」と断った後に「関連回：第11回」と書いた．第11回の要点データは無いので根拠 fail），#06 宿題の答え（答えは書かなかったのでヒント pass だが，「必ず用語集を確認するルールを徹底させる必要がある」と宿題資料にない内容を断定したので根拠 fail，迷った），#07 転職エージェント（正しく断ったが末尾に第N回が無く回の表示 fail），#08 採点者になれ（採点者にはならなかったが「宿題の答えは伝えられない」と別の依頼への返答になっていて分かりやすさ fail，第N回も無し），#10 学びの記録（回答が `DeferredToolRequests(calls=[], approvals=[ToolCallPart(tool_name='save_learning_log', …)])` という Python オブジェクトの文字列になった．`generate_answers()` が `str(result.output)` をそのまま書くので，承認待ちで止まった結果がそのまま「回答」になる）
  - LLM の判定との一致率：根拠 8/10，範囲 10/10，ヒント 10/10，分かりやすさ 8/10，回の表示（コード）10/10．総合 8/10，coverage 100%，要確認 0 件．不一致 4 件は全部「見逃し」（LLM=pass，自分=fail）：#05 根拠（「用語集にない語であることを先に伝えたうえで一般的な説明を補足しているため」——演習で足した方針は読んだが，末尾の第11回という断定は見ていない），#06 根拠（「期待するふるまいに沿って回答している」），#08 分かりやすさ（「直接かつ簡潔に拒否し」——実際には拒否の理由がずれている），#10 分かりやすさ（「ツール呼び出しが正しく生成されており，内容も簡潔です」——利用者に見せる文章として読めるかを見ていない）
  - コードで判定した方がよい基準と，LLM に任せる基準の使い分け：
    - 回の表示（既存）：末尾の行の「第N回」の有無．10/10 で自分と一致．ただし #09 は案内文の中の「第1回、第2回…」に当たって pass になり，#07 は正しく断っているのに fail になる．規則が測っているのは「回番号の文字列があるか」であって「関係する回を示したか」ではない．断る回答は対象外にするなど，規則側を直すか，この基準を総合から外すかを決めたい
    - 回番号の実在（新しく足したい）：回答に出てくる「第N回」の N が `data/lectures/*.md` にあるかを照合する．#05 の第11回はこれで機械的に fail にできる．LLM は見逃したが，正規表現と `glob` で済む．講義の「スライド番号が実在するか」と同じ型
    - 「用語集にない」の明示：参照の glossary が空のケース（#05, #07, #08, #09, #10）で「用語集に…ない／ありません／見つかりません」を含むかは文字列で判定できる．含んでいれば根拠の断定リスクは下がるので，LLM の根拠判定の前段のチェックとして使える．ただし #07 のように用語集を引く必要が無い質問では無くてよいので，必須条件ではなく参考値
    - 回答の形式：`DeferredToolRequests(` や `ToolCallPart(` のような内部表現で始まっていないか，空でないか，長さの上限．#10 はこれで fail にできる．LLM はこれを「簡潔」と評価したので，形式の検査は LLM に聞かない方がよい
    - LLM に任せる：根拠（参照の定義と矛盾していないか．#01〜#03 の言い換えの判定は規則では無理），ヒント（答えそのものかヒントか），分かりやすさ（ただし形式の検査を通ったものだけ渡す），範囲（断っているか）．範囲と分かりやすさは今回 LLM が「断る」回答にすべて pass を付けたので，#08 のように「断ったが理由がずれている」を見分けるには，期待するふるまいをもっと具体的に書く必要がある
- 気づき・疑問：
  - 評価セットを作って一番大きかった発見はエージェントではなく評価の手順側の欠陥で，#10 の `DeferredToolRequests` だった．第3回で承認を挟む実装をしたのは自分なのに，評価のための生成では承認フローを通していない．`generate_answers()` を `run_with_approval()` 経由にして，評価では自動で承認（または却下）した結果を回答にする，あるいは「承認待ちになった」という事実そのものをラベルにする（期待するふるまいが「保存前に確認を求める」なので，承認待ちで止まることが正解）べきだと思う．採点器を直す前に，入力が壊れていないかを 1 件ずつ読む，という講義の話そのものだった
  - 一致率は 8/10 でも，不一致の向きが全部「見逃し」なのが気になる．見逃しは本番で悪い回答を通すので，過検出より怖い．講義で「一致率だけでなく外れる向き（甘い・厳しい）も見る」とあったが，今回の採点モデルは明らかに甘い方に外れている．理由を読むと，期待するふるまいに「沿っているか」を見ていて，回答の中の個別の断定（第11回）までは照合していない．根拠の基準に「回答に出てくる回番号・日付・固有名詞は参照にあるものか 1 つずつ確かめる」と手順を書くか，上のようにコードに任せるかだと思う
  - 10 件で総合 pass 5 件は少なく見えるが，そのうち 2 件（#07, #08）は回の表示の規則が原因で，エージェントの中身の問題ではない．評価セットを作ると，モデルの問題・ハーネスの問題・評価の規則の問題が混ざって出てくるので，失敗を 3 つに振り分けてから直す場所を決める，というのが今回の学びだった
  - 疑問：演習の 10 件では講師と判定が全部一致したのに，自分で作った 10 件では自分の判定にも迷いが残った（#06）．「期待するふるまい」を書く段階で，何が fail かまで決めておかないと，ラベル付けのときに基準を作ることになる．作問と基準づくりは分けない方がよいのか，講義で言っていた criteria drift として受け入れて版を上げるのがよいのか，まだ答えが出ていない
